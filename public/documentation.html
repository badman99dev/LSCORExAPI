Complete reference for the LSCORExAPI — a high-performance REST + SSE live cricket score API backed by CREX feeds. Every endpoint, parameter, and response shape explained with copy-paste examples.

🌐 Overview

LSCORExAPI exposes live cricket data as clean JSON. It supports two access models:

REST endpoints return a one-shot JSON snapshot. SSE endpoints keep an open stream and push diffs on every ball, so you never have to poll.
Common list response shape
{
  "success": true,
  "sport": "cricket",
  "source": "crex",
  "tab": "live",
  "count": 5,
  "matches": [ /* array of match summary objects */ ]
}

Every single-object endpoint wraps its payload as { success: true, match: {...} }, { success: true, team: {...} } (team), or { success: true, ...payload } (series).

📡 SSE Live Stream

SSE/matches/:id/streamTry ↗
Canonical infinite Server-Sent Events stream. Sends an initial snapshot, then streams update diffs on every change, plus heartbeats. Non-live matches (upcoming/finished) get one snapshot then a closing end. Alias: /events/:id/stream.
ParamTypeDescription
delayoptionalSeconds to lag behind live (DVR mode). Range 0–60. Default 0.
Event types
eventPayload
snapshot{ match, cached, delayMs }
update{ id, timestamp, changes:[{path,from,to}], match }
end{ matchId, reason } — stream will close
JavaScript example
const es = new EventSource(
  "https://lscorexapi.onrender.com/matches/11AM/stream"
);

es.addEventListener("snapshot", (e) => {
  const { match } = JSON.parse(e.data);
  console.log("initial:", match.statusText);
});

es.addEventListener("update", (e) => {
  const { changes } = JSON.parse(e.data);
  changes.forEach((c) => console.log(c.path, c.from, "->", c.to));
});

es.addEventListener("end", (e) => {
  console.log("match ended", JSON.parse(e.data));
  es.close();
});
DVR tip: append ?delay=30 to watch the match 30 seconds behind live — perfect for syncing with a video feed. Delayed clients still receive the terminal end event.

⭐ Advanced Match Finder

Find a fixture two ways — by two team names or by a series name — always with a required startTime. Returns the matching fixture object plus how confident the time match is.

GETPOST/find-matchTry ↗
Advanced finder. Aliases: /match-finder, /api/find-match.
Two modes. Provide startTime plus either series or both team1 & team2. startTime accepts epoch milliseconds since 1970 (e.g. 1822896000000) or a datetime string like 2026/10/09 13:30:14 +0000.
ParamTypeDescription
startTimerequiredMatch start time. Accepts epoch milliseconds since 1970 (number or numeric string) or a datetime string YYYY/MM/DD HH:mm:ss +ZZZZ (e.g. 2026/10/09 13:30:14 +0000; - separators, optional seconds & timezone also work). Aliases: start_time, time, start, date.
seriesrequired*Series/tournament name to search. Aliases: seriesName, tournament. *Use series or the two teams.
team1optionalFirst team search term (team mode; also an optional filter in series mode). Aliases: teamA, t1, home, team.
team2optionalSecond team search term (team mode; also an optional filter in series mode). Aliases: teamB, t2, away, opponent.
toleranceMsoptionalMax |delta| for time matching. Default 10800000 (3h). Alt: toleranceMin.
topNoptionalTeam mode only: how many team search hits to consider per team. Default 2.
Mode A — by teams
  1. Searches both team names → takes the top topN Team results for each.
  2. For combos 1x1 → 1x2 → 2x1 → 2x2, fetches both teams' Team Matches & Tours and intersects by match id.
  3. First combo with a time match wins; else the closest fixture is returned.
Mode B — by series
  1. Searches the series name (Series and Other tour entities).
  2. Prioritises editions whose year matches startTime, then probes their fixtures.
  3. Returns the series match closest to startTime. Optional team1/team2 filters within the series.
Time-match classification
timeMatchTypetimeMatchMeaning
exacttrueFixture start equals startTime exactly.
within-tolerancetrueWithin toleranceMs (default 3h).
same-daytrueSame UTC day, but beyond tolerance.
closestfalseNo time match; nearest fixture returned as fallback.
nonefalseNo common fixture at all (matched: false).
Examples
# Team mode — epoch milliseconds
GET /find-match?team1=India&team2=Australia&startTime=1822896000000

# Team mode — datetime string with timezone
GET /find-match?team1=India&team2=Australia&startTime=2026/10/09%2013:30:14%20%2B0000

# Series mode
GET /find-match?series=World%20Cup%202027&startTime=2027/10/07%2008:00:00%20%2B0000

# Series mode + team filter
GET /find-match?series=Australia%20tour%20of%20South%20Africa%202026&team1=Australia&startTime=2026/10/20%2008:00:00%20%2B0000

# POST body
POST /find-match
{ "series": "World Cup 2027", "startTime": "2027/10/07 08:00:00 +0000" }

Check timeMatchType: closest means no fixture fell inside the time window, so the nearest one was returned as a best-effort guess — always verify timeDeltaMs. When there is no common fixture at all, matched is false with a reason.
Series-mode cache (1 day)
Series searches and their fixture lists are cached for 24 hours (series & fixtures rarely change), so repeated queries are ~instant. Inspect or clear it any time:
GET  /find-match/cache          # { success, cache: { ttlMs, searchEntries, matchesEntries, searchKeys, matchesKeys } }
POST /find-match/cache/clear    # wipes the 24h cache
