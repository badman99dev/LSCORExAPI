Layout that reads like a broadcast

A score screen gets about a second of attention between deliveries. Build the hierarchy so that second is enough.

  • Make the score the loudest thingRuns and wickets at 56–64px in a condensed numeral face. Everything else sits at a third of that size or less.
  • Order the screen by how fast it changesScore, chase line, batters, this over, bowler, partnership. The data that moves every ball lives where the eye already is.
  • Say the chase as a sentence"Need 44 off 22" lands faster than "RRR 12.00". Keep both, but make the run rates small secondary chips.
  • Give each colour one jobRed is live and wickets, blue is a four, violet is a six, amber is an extra. After a few balls viewers read the over without reading a letter.
  • Let team colour glow, not fillUse colors.primary from /team/:id as a soft radial behind the score card. Keep surfaces neutral and dark so jerseys and faces are the brightest things on screen.
  • Celebrate once per ballOne banner (FOUR, SIX, WICKET) plus the rolling number is enough. Animating the whole screen on every update makes it feel nervous.

The jersey with the head tucked in

Two transparent PNGs in one square box. The jersey is the base, the player's head sits on it and its lower edge melts into the collar, so it looks like he's wearing the shirt. Tune it on the right — the phone above updates too.

  • One box, always the same ratioFix the aspect ratio on the wrapper so every player lines up in a squad grid, whatever the image sizes are.
  • Head about 40% of the jersey widthLet it overlap the collar by roughly a tenth of the box height. Too big and it reads as a sticker, too small and it disappears.
  • Fade the bottom of the headA 20–30% mask on the lower edge makes the neck dissolve into the collar instead of ending in a hard line.
  • Add a contact shadow under the chinA soft dark ellipse between head and jersey is what tells the eye the head is inside the shirt.
  • Transparent neckline? Go behindIf the jersey PNG has a see-through collar, switch to "Behind jersey" and let the shirt overlap the head for real.
  • Match the formatUse jersey/limited/ for ODI and T20, jersey/test/ for Tests. The API already returns the right one in rich.striker.jersey.
  • Never let a broken image jump the layoutKeep the box size, hide a failed image with onerror, and show initials or a silhouette behind it.

Digits that roll when the score moves

      
Every digit lives in its own column of 0–9. When the value changes, the column slides to the new digit. Nothing is re-rendered, so 149 → 150 moves two columns and leaves the 1 alone.


      

        
    
          
  • Animate only the digits that changedCompare per column, or react to the paths in the SSE changes array. The eye follows the part that moved.
    • 
          
  • Roll up when it grows, down when it dropsRuns only climb, but required run rate and balls left fall. Direction tells the story for free.
    • 
          
  • Tabular numerals, clipped to one lineSame-width digits stop the number wobbling. Clip each column to 1em so only the current digit shows.
    • 
          
  • 500–700ms, fast out, slow inIf a second update lands mid-roll, CSS just retargets the transform. No queue needed.
    • 
          
  • Overs wrap at 6, not 10The ball digit goes 5 → 0, so give it a base-6 column. The demo uses roll(el, value, 6).
    • 
          
  • Pair the roll with one flashA 900ms tint (blue four, violet six, red wicket) tells viewers why the number moved.
    • 
          
  • Don't animate the snapshotThe first paint should jump into place. Only update events roll.

Showing overs so they read at a glance

      
Overs are the one number people misread most. Store balls, show chips for the over in progress, and keep the history one glance away.


      

        
    
          
  • 16.2 is 16 overs and 2 ballsIt is not a decimal. 16.5 plus one ball is 17.0, not 16.6. Keep a ball count and format it for display only.
    • 
          
  • Compute rates from ballscrr = runs / balls * 6 and rrr = (target - runs) / (total - balls) * 6. The API already gives score.balls.
    • 
          
  • Always show six slotsEmpty placeholders keep the card the same height. The next slot gets a soft pulse so people know where the next ball lands.
    • 
          
  • Extras add a chip, not a slotA wide or no-ball is not a legal delivery, so the over grows by one chip and the placeholders stay put.
    • 
          
  • Colour plus a glyphDot for 0, the number for runs, W for a wicket, Wd for a wide. The glyph keeps it readable for colour-blind viewers.
    • 
          
  • Hold the finished overLeave the completed six on screen until the next ball arrives, then move it into the history. No timers needed.
    • 
          
  • One bar for the whole inningsTwenty segments, the current one filling ball by ball, powerplay overs tinted slightly.

Balls ⇄ overs, the safe way

      
const fmtOvers = balls => `${Math.floor(balls / 6)}.${balls % 6}`;   // 98  → "16.2"
const toBalls  = ov    => { const [o, b = 0] = String(ov).split('.'); return o * 6 + +b; }; // "16.2" → 98

const crr = (runs, balls) => balls ? (runs / balls * 6).toFixed(2) : '0.00';
const rrr = (target, runs, balls, total = 120) => (target - runs) / (total - balls) * 6;

      
Map commentary balls to chips

      
// GET /matches/:id/commentary  →  recentBalls[]
const chipFor = b =>
  b.isWicket   ? { cls: 'cw', text: 'W' }  :
  b.isExtra    ? { cls: 'cx', text: 'Wd' } :   // read the label from b.text for nb / lb
  b.isBoundary ? { cls: runs(b) === 6 ? 'c6' : 'c4', text: String(runs(b)) } :
                 { cls: runs(b) === 0 ? 'c0' : 'c1', text: runs(b) === 0 ? '•' : String(runs(b)) };

    

  


  
  

    

      
Wire it to the stream

      
Paint once from the snapshot, then let each update touch only what changed. The changes array tells you which paths moved, so it also tells you which animation to play.

Stream handler

      
const es = new EventSource(`${BASE}/matches/${id}/stream`);   // add ?delay=30 to sync with a video feed

es.addEventListener('snapshot', e => {
  paint(JSON.parse(e.data).match, { instant: true });        // jump into place, no rolling
});

es.addEventListener('update', e => {
  const { changes, match } = JSON.parse(e.data);
  paint(match, { instant: false });
  for (const c of changes) {
    if (c.path === 'rich.striker.runs' && c.to - c.from === 4) banner('FOUR');
    if (c.path === 'rich.striker.runs' && c.to - c.from === 6) banner('SIX');
    if (c.path.endsWith('score.wickets'))                   banner('WICKET');
  }
});

es.addEventListener('end', () => es.close());               // upcoming / finished matches end after one snapshot

function paint(m, { instant }) {
  const bat   = m.teams.team1.isBatting ? m.teams.team1 : m.teams.team2;
  const balls = bat.score.balls;
  roll(runsEl,   bat.score.runs,    10, instant);
  roll(wktsEl,   bat.score.wickets, 10, instant);
  roll(ovIntEl,  Math.floor(balls / 6), 10, instant);
  roll(ovBallEl, balls % 6,             6,  instant);
  strikerImg.src = m.rich.striker.head;                       // the browser skips the reload if the URL is unchanged
  jerseyImg.src  = m.rich.striker.jersey;
}


      
What makes a live screen feel cheap

      
    
        
  • Rolling on the first paintEvery number spinning when the page opens looks like a slot machine. Snapshot jumps, updates roll.
    • 
        
  • Overs as a decimal16.5 + 0.1 = 16.6 is a bug people notice. Store balls.
    • 
        
  • Remounting components per updateMutate the existing nodes. Rebuilding the tree restarts every animation and flickers images.
    • 
        
  • Three animations per ballOne focal moment per delivery: the banner and the number. Everything else stays still.
    • 
        
  • No fallback for imagesCDN images fail sometimes. Keep the box, hide the broken image, show initials.
    • 
        
  • Ignoring the end eventClose the stream and flip the pill from LIVE to the result when end arrives.
